# 08 — Design decisions cheatsheet

> **What this answers.** A one-line summary of each of the 14
> design decisions in `docs/design-decisions.md`. Read this
> before the interview; you'll be tested on the *why* more than
> the *what*.

---

## The full list, one line each

### 1. Mock planner + Mock LLM as the demo default
Default to deterministic; switch to real LLM with one config
flag. Hermetic demo, no API key required.

### 2. In-memory conversation store
Process-local `dict` keyed by `conversation_id`. Small API,
swappable later. SQLite / Redis rejected as too heavy for
the brief's timebox.

### 3. Sequential chain runner
v1 runs plan steps in order; wave-aware schema is in place
for future parallel execution. DAG executor rejected as too
much complexity for the demo.

### 4. Template-projected Incident (no LLM prose)
The structured `Incident` is built from MCP outputs and a
template — *not* generated by the LLM. The LLM only writes
the natural-language summary. The structured shape is
deterministic, testable, and never hallucinates a severity.

### 5. Ticket-mock as the only ticketing backend
A real ticketing system (Jira / Azure DevOps / ServiceNow /
GitHub Issues) was an option. Mock chosen because the MCP
exposure is what matters for hard constraint #3; the mock
exercises the same code path.

### 6. Streamlit for the GUI
Python-only, no bundler. React + FastAPI was too heavy for
the 10-14 hour timebox. Gradio was less flexible for the
workspace column.

### 7. ChromaDB at build-time, in-memory numpy at runtime
ChromaDB is wired for production paths; the demo uses a
simple numpy index persisted to `var/index/v1.pkl`. Same
interface, different storage. Hermetic demo, no separate
service to spin up.

### 8. Deterministic embedder as the demo path
A hash-based function that returns the same vector for the
same input every run. Tests are reproducible; production
swaps to `sentence-transformers` with a one-line config.

### 9. Single planning step (no separate prompt-engineering module)
The planner is one Python file. A separate
prompt-engineering module was rejected as over-engineering
for the timebox.

### 10. Connection-pool-per-MCP-client (no global pool)
Each `MCPClient` owns its connection pool. Cross-process
pools were rejected as overkill for v1; per-client pools
are simpler to test.

### 11. In-process FastAPI `TestClient` for integration tests
Tests use `httpx.AsyncClient` against the in-process FastAPI
app — no Docker-in-Docker, fast CI. Real-Docker testing is
left to `docs/deployment-verification.md`.

### 12. Streamable HTTP transport (not stdio) for MCP
HTTP-native, composes with FastAPI middleware, no WebSocket
quirks. Stdio is fine for desktop tools but awkward for
service-to-service.

### 13. 471 tests, not 1000
Quality over quantity. The test pyramid is unit-heavy;
integration covers wiring; one e2e test covers the happy
path. Adding tests for the sake of numbers was explicitly
rejected.

### 14. Structured `Incident` (not raw alarm-api output)
The orchestrator projects the alarm API's raw fields into a
clean `Incident` schema. Keeps the orchestrator agnostic
to changes in the alarm API's response shape.

## Likely interview questions

**Q: "What's the most important design decision in this
project?"**

> Decision #4 — the `Incident` is template-projected, not
> LLM-generated. The structured shape is what makes the
> ticket pre-fill deterministic and what makes the audit
> log meaningful. The LLM is only allowed to write
> narrative text.

**Q: "What would you do differently with more time?"**

> Turn on the wave-aware executor (decision #3). The schema
> supports it; the runner just doesn't dispatch parallel
> steps yet. With two parallel MCP calls we'd shave ~30% off
> the per-request latency.

**Q: "Why didn't you use a real ticketing system?"**

> Decision #5. The brief's hard constraint #3 is about the
> approval gate, not the ticketing vendor. The mock exercises
> the same code path; swapping to Jira is a connector change.

**Q: "Why 471 tests and not more?"**

> Decision #13. Quality over quantity — each layer's tests
> target the bugs that layer is good at catching. Adding
> tests for the sake of numbers slows CI without improving
> signal.
